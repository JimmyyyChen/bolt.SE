bolt.SE

Making AI-generated code follow API specs, pass tests, and run through CI/CD.

My 2025 undergraduate project at Tsinghua University’s School of Software. I extended bolt.diy, an open-source tool that builds web apps from chat prompts inside the browser, with four modules that give the model real API specifications, tests to pass, access to external tools, and a path to a delivery pipeline.

Demo: from prompt to pipeline

A natural-language task manager is built with an attached API and supplied tests. The workflow then continues into GitLab through MCP.

  1. Attach the OpenAI API and the test file

  2. Generate code, run the tests, and start the app 4×

  3. Use the app; four task-operation tests pass

  4. Generate the GitLab CI configuration 3×

  5. GitLab MCP: create the repository and push code 4×

  6. The pipeline runs and fails at dependency installation

What I built

Four modules on top of bolt.diy’s existing editor, model integration, and in-browser runtime. The work spans the UI, persistence, server routes, and the action runner of an existing TypeScript/Remix codebase, plus English/Chinese localization.

01

API-first development

Problem. Models guess at APIs they cannot see.

What I built. An API Actions manager. You paste an OpenAPI schema (YAML or JSON) and choose an auth type; its operations are parsed automatically and the definition is saved in IndexedDB. Selected APIs are added to the model’s context and shown as tags on the message.

  1. Paste spec
  2. Parse operations
  3. Select the API
  4. Generate against it

02

Test-driven development

Problem. Generated code is rarely checked against the behavior it should have.

What I built. A test editor that parses describe/it blocks into a navigable tree. Tests are written into the project before generation. A new test action runs Jest-style tests with Vitest in the browser runtime. When a run fails, an “Ask Bolt” button sends the failing output back to the model for repair.

See it: Calculator failure → repair

03

MCP integration

Problem. The model cannot see live systems such as databases or repositories.

What I built. Server-side Model Context Protocol clients over stdio and SSE, plus a configuration panel that checks availability and lists each server’s tools. The tools go to the model for multi-step calling (up to 20 steps), and each call and its result appear in the chat as a tool record.

  1. Configure server
  2. Discover tools
  3. Model calls tools
  4. Results return to chat

04

CI/CD

Problem. Generated apps stop at a local preview, disconnected from delivery.

What I built. A workflow that combines TDD with GitLab MCP tools. The model writes GitLab CI configuration, creates a repository, and pushes the code; the push triggers a pipeline configured to test and deploy.

Result. The pipeline was triggered and failed at dependency installation. Deployment to Vercel was not verified.

IoTDB dashboard: MCP and API-first

The model inspects a live IoTDB database through MCP, then builds a battery-data chart that reads from the attached IoTDB REST API.

  1. Set up the IoTDB MCP server (three tools) and the REST API

  2. Inspect the database through MCP, then generate 4×

  3. Explore the chart; ask for a white background

  4. Apply the revision 3×

  5. Check the revised dashboard and tool results

Calculator: test failure and repair

To exercise the feedback loop, I changed one assertion to expect(add(2, 3)).toBe(0). The test failed, the model added a special case, and all 12 tests passed again. This shows the model responding to test feedback; the changed requirement is deliberately wrong, so it says nothing about arithmetic correctness.

Architecture

The four modules sit on top of the bolt.diy pipeline: model output is parsed into files and commands, then run in a browser runtime. CI/CD reuses the TDD and MCP mechanisms.
